# 词条实现场景手册

面向 AI 与 Mod 开发者的场景式教程。想新增一个词条（Entry），先在本手册里判定它属于哪一类，复制对应模板改。

本手册与其他文档的分工
    子系统/物品/词条系统.md — EntryDefinition 结构、EntryModifier 生命周期、注册流程
    参考/反应系统详解.md — reaction/action 声明式模式（触发器挂载类词条会用到）
    子系统/属性与当前值/属性系统.md — Status 层（status 语法糖类词条会用到）
    本手册 — 我要做「XX 词条」，选哪类，模板怎么抄

## 使用方法

词条按实现模式分三类。选择流程：

```
词条要做什么？
    改变卡自身的方法行为（打出后去哪、能否被使用等） → 场景 1（方法覆盖类）
    响应 owner 的事件（回合末/战斗开始/受伤等）      → 场景 2（触发器挂载类）
    表征一个"可查询 flag"，未来别的效果也可能挂它    → 场景 3（status 语法糖类）
```

每个场景的模板都是**在 CardEntry.ts 里加一条 EntryDefinition**。不需要改其他文件，除了：
    场景 2 涉及新 EffectFunc — 在 `entryEffects.ts` 写函数并注册到 `effectMap.ts`
    场景 3 涉及新 status — 在 `statusMap.ts` 里注册

## 场景 1：方法覆盖类（改变卡的行为方法）

目标
    「打出后回抽牌堆」「打出后进消耗堆」——词条改变的是**卡本身的一个方法**（这里是 `getAfterUseEffect`），不涉及事件监听。

涉及机制
    onApply 内保存原方法引用，覆盖为新方法
    返回一个恢复函数（词条被 removeEntry 时用来恢复原方法）

数据模板：打出后回抽牌堆（`card_return_to_draw`）

```typescript
card_return_to_draw: {
    label: "回归",
    describe: ["使用后，将其洗回抽牌堆"],
    conflictsWith: ["card_exhaust", "card_ability"],  // 与其他"使用后去向"互斥
    onApply: (owner, ownersOwner) => {
        const result = checkOwnerTypes(owner, ownersOwner)
        if (!result) return []
        const { card } = result

        const originalMethod = card.getAfterUseEffect.bind(card)

        card.getAfterUseEffect = (fromPile) => ({
            key: "pay_returnToDraw",
            describe: ["将卡牌洗回抽牌堆"],
            params: { sourcePile: fromPile, card }
        })

        return [() => {
            card.getAfterUseEffect = originalMethod
        }]
    }
}
```

要点
    `conflictsWith` 需覆盖所有"使用后去向"类词条 —— 目前包括 `card_exhaust` / `card_ability`（详见 词条系统.md 冲突关系）
    覆盖时先 `bind(card)` 保存原方法，不然 this 会丢
    恢复函数必须精确恢复到覆盖前的方法引用，否则多次挂/卸会串味
    新的 pay_XXX EffectFunc 要在 entryEffects.ts 写并注册到 effectMap.ts

参考实例
    `card_exhaust` — 打出进消耗堆
    `card_ability` — 打出移出战斗

## 场景 2：触发器挂载类（响应 owner 的事件）

目标
    「回合结束时若在手，则消耗」「战斗开始时进入手牌」「打出后每回合结束抽 1 张」——词条要**监听 owner 身上的事件**才能发挥效果。

涉及机制
    onApply 内给 ownersOwner（通常是 Player）挂 reaction + trigger
    reaction 挂在 ownersOwner.reaction 上
    trigger 通过 `createTriggerByTriggerMap` + `appendTrigger` 挂载
    返回 remove 函数（词条卸载时清理 trigger）

数据模板：回合结束时抽 1 张（`card_end_turn_draw`）

```typescript
card_end_turn_draw: {
    label: "延续",
    describe: ["回合结束时抽 1 张牌"],
    onApply: (owner, ownersOwner) => {
        const result = checkOwnerTypes(owner, ownersOwner)
        if (!result) return []
        const { card, player } = result

        if (!player.reaction) player.reaction = {}
        player.reaction.endTurnDrawByEntry = [{
            key: "endTurnDrawByEntry",
            label: "延续：抽 1 张牌",
            targetType: player,
            effect: [{
                key: "drawCard",
                describe: ["抽 1 张牌"],
                params: { value: 1 }
            }]
        }]

        const triggerObj = createTriggerByTriggerMap(player, player, {
            when: "before",
            how: "make",
            key: "turnEnd",
            level: -10,        // 让 inHand 类触发器先执行
            onlyKey: `endTurnDrawByEntry_${card.__id}`,  // 每张卡独立触发器
            action: "endTurnDrawByEntry"
        })

        const { remove } = player.appendTrigger(triggerObj)
        return [remove]
    }
}
```

要点
    trigger 挂在 ownersOwner（player/enemy），不是 owner（card 本身）
    `level` 需要考虑与 inHand 触发器的执行顺序 —— 想在 inHand 触发器**之后**执行就写负数
    `onlyKey` 加卡的唯一标识，防止同一玩家多张同词条卡的触发器互相踩
    如果需要复杂副作用，把 reaction 内的 EffectUnit 拆到独立 EffectFunc（写在 entryEffects.ts）
    remove 函数由 `appendTrigger` 返回，直接放进 removers 数组

参考实例
    `card_void` — 回合末消耗未打出的卡
    `card_inherent` — 战斗开始抽固有卡

## 场景 3：status 语法糖类（挂 status flag）

目标
    「回合结束时不弃入弃牌堆」「不能被主动打出」——词条要表达的是"卡带某个 flag"，而且**未来别的效果也可能想挂同样的 flag**（临时保留 / debuff 禁用等）。

涉及机制
    在 statusMap.ts 注册一个 status
    onApply 里给 card 挂 status（value=1）
    返回移除 status 的函数
    真正读取该 status 的**逻辑放到相关代码**（如 CardModifier 的判定函数里查 status，不查词条）

数据模板：临时不能打（新词条 + 新 status）

第一步：在 `statusMap.ts` 注册新 status
```typescript
"cannot-play": {
    label: "不可打出",
    value: 0,
    describe: "大于 0 时，该卡无法主动打出",
    category: "card",
    hidden: true,
    notNegative: true
}
```

第二步：在 CardEntry.ts 加词条（挂 status 的语法糖）
```typescript
card_cannot_play: {
    label: "不能被打出",
    describe: ["该卡牌无法被使用"],
    onApply: (owner, ownersOwner) => {
        const result = checkOwnerTypes(owner, ownersOwner)
        if (!result) return []
        const { card } = result

        ensureStatusExists(card, "cannot-play", 0)
        const removeStatus = changeStatusValue(card, "cannot-play", "card_cannot_play", {
            value: 1,
            type: "additive",
            target: "base"
        })
        return [removeStatus]
    }
}
```

第三步：**改判定逻辑**读 status 而非 hasEntry
```typescript
// CardModifier.canPlayCard
if (
    ifHaveStatus(card, "cannot-play") &&
    (getStatusValue(card, "cannot-play") as number) > 0
) {
    return `该卡牌无法被打出`
}
```

要点
    真相源是 **status**，词条只是最基础的挂载来源之一
    `changeStatusValue` 返回的 remove 函数直接进 removers 数组，词条卸载时自动清理
    `notNegative: true` 防止 status 被减到负数
    未来做「临时保留一回合」类效果时，直接给卡挂 status，不需要动词条系统
    `category` 用 `"card"`，`hidden: true` 让它不出现在 UI 属性列表里

参考实例
    `card_retain` — retain-on-turn-end
    `card_cannot_play` — cannot-play

## 附录 A：决策流程

新词条从需求到实现模式的判定：

```
1. 问：这个词条改的是"卡自己的一个方法"吗？
     是 → 场景 1（方法覆盖类）。改哪个方法？currently 主要就 getAfterUseEffect
     否 → 继续

2. 问：这个词条需要"在某个事件发生时做点事"吗？
     是 → 场景 2（触发器挂载类）。挂到谁上？
           响应 owner 的事件（turnEnd/battleStart） → 挂 ownersOwner
           响应 card 本身的事件（use/lost） → 挂 owner（少见）
     否 → 继续

3. 问：这个词条是"卡具有 XX 特质"这种可查询 flag 吗？
     且这个 flag 未来可能被别的效果挂？
     是 → 场景 3（status 语法糖类）。同时改判定处读 status
     否 → 重新想需求，多半可以拆解成上面三类的组合
```

## 附录 B：常见坑

    忘写 `conflictsWith`：跟已有词条语义重叠时容易多挂 → 声明清冲突关系
    conflictsWith 声明**只需单向**：EntryModifier.addEntry 会双向查，A→B 冲突就够，不必 B→A 再写一次（但**推荐双向声明**便于阅读）
    方法覆盖时 `this` 丢失：`getAfterUseEffect = ...` 里覆盖后新方法读 card 字段会 undefined → 直接引用 `card` 变量，别用 this
    触发器 level 忘设：与 inHand 触发器冲突时执行顺序乱 → 明确 level（负数=后执行）
    reaction key 重名：多个词条如果 reaction 名冲突后挂的覆盖先挂的 → 加词条前缀区分
    status 语法糖类忘了改判定逻辑：只挂 status 不改代码等于没做事 → 挂 + 改 + 测三步都要
    onApply 不返回移除函数：卸载时不清理副作用 → 至少返回 `[]`
    owner 类型不匹配：`checkOwnerTypes` 断言失败就返回 `[]` → 保护主逻辑
    ensureStatusExists 遗漏：直接 changeStatusValue 会报错 → 先 ensure 再 change

## 快速对照表

想实现的词条行为 → 场景编号

    改变打出后去向（消耗/移出/回抽等） → 1
    改变卡的其他自身方法（canPlay/getDescribe 等） → 1
    响应回合/战斗事件做点事 → 2
    响应"抽到本卡""失去本卡"事件做点事 → 2
    "卡是否具有 XX 特质"类可查询 flag → 3
    临时性效果（也可能来自 debuff / 状态） → 3
