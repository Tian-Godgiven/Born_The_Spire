# 常见错误排查手册

按主题分类的跨类型错误集。写新内容时对照检查，遇到诡异行为时来这里查。

每份场景手册末尾都有该类型专属的错例。本手册聚焦跨类型的**通用陷阱**，特别是事件系统 / 修饰器 / 触发器这些基础机制。

## 使用方法

看到症状 → 用 Ctrl+F 搜关键词
    「不生效」「没触发」「刷新丢失」「双倍触发」「Vue reactive」「Cannot access」「循环依赖」

按分类浏览
    A. 事件系统绕过 — 最常见、后果最严重的一类
    B. 修饰器生命周期 — 「要不要写 lose 段」这个问题
    C. 触发器 when / how / key — 触发时机与角色定位
    D. action / reaction 断链 — 写了 triggers 但没触发
    E. 数据结构位置 — cost、target、pool 之类的字段位置
    F. 多段与群体 — 事件语义正确的关键
    G. 状态定义细节 — allowNegative / stackChange 陷阱
    H. 表达式与引用 — $xxx 语法与 status key 名
    I. 描述文本 — describe / label 引用陷阱
    J. AI behavior — 敌人特有的坑
    K. 设计原则违反 — 器官对称 / 独立 / Boss 泄漏
    L. 模块加载顺序 — Cannot access before initialization、动态 import 误用

## A. 事件系统绕过

### A1. 直接修改 Entity 属性

症状
    数值改了但触发器不响应；护甲、修饰器计算不对；UI 有时不刷新

错例

```typescript
player.current.health.value -= 10
enemy.status["max-health"].base += 5
organ.status["heat"].value = 0
```

正解

```typescript
doEvent({
    key: "attack",
    source: enemy, medium: card, target: player,
    effectUnits: [{ key: "attack", params: { value: 10 } }]
})

// 或者通过 effect 走：
{ key: "addStatusBase", params: { statusKey: "max-health", value: 5 } }
{ key: "addCurrent", params: { statusKey: "heat", value: -organ.current.heat } }
```

为什么
    所有游戏状态变更必须通过事件系统，否则触发器无法介入、修饰器无法记录、Vue 响应式无法追踪
    参考：CLAUDE.md 「不得绕过效果系统」

### A2. 直接修改 State 的 stacks

错例

```typescript
state.stacks -= 1
```

正解

```typescript
{ key: "changeStateStack", params: { stateKey: "poison", delta: -1 } }
{ key: "removeState", params: { stateKey: "poison" } }
```

### A3. 直接调用 Modifier 方法

错例

```typescript
modifierManager.applyOrgan(organ)
```

正解
    走 `gainOrgan` / `replaceOrgan` 之类的 effect，让事件系统组织

例外：`startNewRun` 中初始器官因为不产生 acquired 事件，可以直接 gainOrgan 效果（这是设计允许的）

### A4. 派发之后立刻读结果，但没有 await doEvent

症状
    治疗/扣费已经派发，下一行读到的还是旧值；选项该置灰却还能点（水池满血仍能饮用）

错例

```typescript
doEvent({ key: "heal", source: p, medium: p, target: p,
    effectUnits: [{ key: "heal", params: { value: 10 } }] })
const hp = getCurrentValue(p, "health")  // 还是治疗前的值
```

正解

```typescript
await doEvent({ key: "heal", source: p, medium: p, target: p,
    effectUnits: [{ key: "heal", params: { value: 10 } }] })
const hp = getCurrentValue(p, "health")  // 治疗已经结算
```

为什么
    doEvent 返回 Promise。自己开新事务时，必须 await 才等到本事件和级联跑完
    已经在事务里时 Promise 立刻 resolve，由外层事务保证顺序
    不 await 也可以（丢出去就走），但紧接着不能读这次派发造成的结果

## B. 修饰器生命周期

### B1. 为清理属性写不必要的 lose 段

症状
    每次改属性型器官都在写重复的 lose effects，代码冗余

错例

```typescript
// 器官提供 +3 最大生命
interaction: {
    possess: {
        effects: [{ key: "addMaxHealthAndHeal", params: { value: 3 } }]
    },
    lose: {
        effects: [{ key: "changeStatusValue", params: { statusKey: "max-health", value: -3 } }]
    }
}
```

正解
    只写 possess，删掉 lose。StatusModifier / ContentModifier 在器官失去时自动撤销

```typescript
interaction: {
    possess: {
        effects: [{ key: "addMaxHealthAndHeal", params: { value: 3 } }]
    }
}
```

力量、中毒这类 **State** 不是 StatusModifier。`possess.effects` 里的 `applyState` 是一次性施加，失去器官不会自动扣层。器官生效期间要挂状态，写 `work.grantStates`，见器官实现场景手册场景 11。

参考：CLAUDE.md 「修饰器清理是自动的」

### B2. 需要写 lose 段的少数例外

有些效果不通过修饰器，必须显式撤销：

```typescript
// 解锁行动型遗物：enabledPoolActions 是 Player 上的 Set
interaction: {
    possess: {
        effects: [{ key: "enablePoolAction", params: { actionKey: "exercise" } }]
    },
    lose: {
        effects: [{ key: "disablePoolAction", params: { actionKey: "exercise" } }]
    }
}
```

识别规律
    走 addStatusBase / gainArmor / addMaxHealthAndHeal / cards — 不写 lose
    走 work.grantStates — 不写 break / lose 扣层，损坏时引擎按差额撤销
    走 enablePoolAction / enableOrganRewardAction / gainReserve — 必须配对 lose
    possess.effects 里的 applyState 是一次性施加，失去不会自动撤；不要用它冒充「生效时拥有该状态」

### B3. 忘写 current 数组导致刷新丢失

症状
    热量 / 累计计数 / mass 之类的当前值在刷新页面后被清零

错例

```typescript
{
    status: { "max-mass": 40, "heat": 0 },
    // current 忘了
}
```

正解

```typescript
{
    status: { "max-mass": 40, "heat": 0 },
    current: ["mass", "heat"]
}
```

规律
    `current` 数组列的是需要**序列化到存档**的当前值 key
    status 里定义的常量默认走 base 层，不需要列
    自定义的可变字段（counter / heat / rust）必须列到 current

### B4. 用手写开战加层、损坏扣层来做「生效时力量」

症状
    损坏后力量还在；或者损坏时把牌给的力量一起清掉；或者扣成 -1 力量

错例

```typescript
work: {
    triggers: [{ when: "after", how: "take", key: "battleStart", action: "givePower" }]
},
break: {
    effects: [{ key: "changeStateStack", params: { stateKey: "power", delta: -1 } }]
}
```

正解
    写 `work.grantStates`。引擎在战斗中给层，损坏 / 失去 / 战斗结束只撤这份赠层。

```typescript
work: {
    target: { key: "self" },
    grantStates: [{ stateKey: "power", stacks: 1, fromLevel: 3 }]
}
```

为什么 work 触发器不够
    work 只是事件监听器。损坏时先拔监听器，再发 breakOrgan，监听器听不到这次损坏
    `applyState` 加出去的层打在玩家身上，和器官脱钩
    力量允许负层，手写 -1 在层已被清光时会变成 -1

参考：器官实现场景手册 场景 11

## C. 触发器 when / how / key 用错

### C1. make vs take 混淆

规则

    `how: "make"` — 持有者是事件的**来源**（我在做这件事时触发）
    `how: "take"` — 持有者是事件的**目标**（这件事发生在我身上时触发）
    `how: "via"` — 持有者是**媒介**（比如卡牌 / 器官作为效果的载体）

对照

    石肤（攻击伤害 -1）→ 玩家挨打 → 玩家是 target → `how: "take"` + `key: "attack"`
    力量（造成攻击伤害 +N）→ 玩家造成挨打 → 玩家是 source → `how: "make"` + `key: "attack"`
    开战 / 战斗结束给自己加东西 → 角色是这条生命周期事件的 target → `how: "take"`（现行：薄翅、壁垒开局护甲、腐化腺开战、熔铸魂、铁壁核心、学者遗物抽牌）

SMT 语义（source / medium / target）

    `battleStart` / `battleEnd` 不是玩家对敌人做的事，是每个人自己进入/离开战斗。每人一条，三方都是自己。
    发生在自己身上 → `take`。写成 `make` 是 SMT 用错：把「我开打了」当成「我发起了开战」。
    旧实现里敌人那条 `battleStart` 的 source 还是玩家，玩家 `how: "make"` 会按敌人数再跑一遍（薄翅 3 层变成 6）。
    现在敌人那条 source 是敌人自己；内容侧开战触发器一律 `take`。

    `turnStart` 一般也是发生在自己身上，内容数据用 `take`。中毒扣血故意挂 `make` 是为了排在护甲清零之后，见 `stateList` 中毒注释，不要跟着抄成开战模板。


错例

```typescript
// 想做「造成伤害时增加」但写成 take
{ when: "before", how: "take", key: "attack", action: "power" }
// 结果：玩家自己受伤时才触发力量，语义完全反了
```

### C2. before vs after 用错

规则

    `when: "before"` — 效果执行前，改参数（蚀伤、易伤、力量、飞飘/飞行减半）
    `when: "on"` — 固定在 before 之后。护甲吸收挂这里，不要和 before 抢 level
    `when: "after"` — 效果执行后，做级联响应（造成伤害后回血、受伤后反击）

对照

    减伤类必须 `before`（要在护甲之前改数字）
    反击类必须 `after`（要等对方伤害真的落下）
    施加状态类看情况：想在 applyState 前拦截层数用 before，想在 apply 后额外做事用 after

### C3. battleStart 忘 disableUntil 导致重复

症状
    某个战斗开始触发的效果，在同一场战斗内多次触发

原因
    battleStart 事件可能被 spawnEvent 级联触发，或某些 UI 流程重复引发

正解

```typescript
triggers: [{
    when: "after",
    how: "take",
    key: "battleStart",
    disableUntil: "battleEnd",   // 关键
    action: "gainPower"
}]
```

规律
    battleStart / turnStart 类"生命周期开始"事件都建议加 disableUntil
    disableUntil 值 = 该触发器什么时候重新生效（下次 battleEnd / turnEnd 之后）

### C4. 打人写成 damage 而不是 attack

症状
    石肤、护甲、力量、虚弱、易伤、飞行不生效；「受到攻击时」类器官不触发；中毒结算却被减伤吃掉

规则

    `attack` 挨打。攻击卡、器官砸、遗物投、遗物/药水砸敌人
    `damage` 受伤但不是挨打。中毒、自残、爆炸自伤
    `loseHealth` 付生命。事件扣血、卡牌生命费。护甲和受伤触发器都不理它
    「受到伤害时」（含中毒）监听 `key: ["attack", "damage"]`

错例

```typescript
// 攻击卡打人
effects: [{ key: "damage", params: { value: 6 } }]
```

正解

```typescript
effects: [{ key: "attack", params: { value: 6 } }]
```

不要让 `attack` 再 spawn 一层 `damage`，触发器会打两遍。

### C5. 把触发器挂在器官 / 卡牌自己身上等回合事件

症状
    器官（或卡牌）实体上挂的 `how: "take", key: "turnEnd"` 触发器永远不响应

原因
    事件系统收集触发器时只看事件的 source / medium / target 这三个实体自己的触发器表，
    不会顺着 `target.organs` 往下找。而 turnStart / turnEnd / battleStart / battleEnd 的
    三个参与者都是角色本身，器官不在其中：

```typescript
// ActionEvent.trigger 的收集范围
this.source.makeEvent(...)   // source
this.medium.viaEvent(...)    // medium
for (const e of targets) e.takeEvent(...)   // target
```

正解
    触发器挂持有者（角色），效果的作用目标指回器官自己。器官数据默认就是这么挂的
    （`resolveTriggerMountTargets` 无 triggerTarget 时返回 `[owner]`），reaction 里用
    `targetType: "item"` 把作用目标指回器官。

    状态的 `stackChange` 已由引擎自动处理：状态挂在器官上时，衰减触发器会挂到器官的持有者
    身上，衰减事件的 target 仍是器官自己，数据侧照常写 `{ timing: "turnEnd", delta: "all" }`。

### C6. 事件 key 拼错或不存在

症状
    triggers 完全没响应，无报错

排查
    查 effectMap.ts 是否有对应 key
    查代码里有没有 `doEvent({ key: "..." })` 用同名 key
    常见拼错：`beginBattle` → 应该是 `battleStart`；`endTurn` → 应该是 `turnEnd`

### C7. 意图预览把真状态写进了器官

旧症状
    刚拿到的过期隔板，下一场开战就带着几层隔板损耗；重锤意图显示 0
    薄翅层数在鼠标划过意图时被扣穿；开战给飞行后被意图预览扣到 0

原因（已改）
    旧预览把真 `before/on/after` 跑一遍，靠 `simulate` 旗到处拦副作用。状态上的飞行扣层、隔板掷骰都会漏。

现行
    意图和卡面走 `previewEffect`：只折叠 `before` / `on` 上 `targetType: "triggerEffect"` 且 key 在 `PREVIEW_PARAM_MODIFIER_KEYS` 里的效果（`modifyDamageValue` / `modifyDamageByPercent` 等）。不跑 `after`。
    扣层、掷骰、护甲吸收不会被调用。过期隔板不进预览。
    `attack` 是挨打，`damage` 是中毒等非挨打，两者都会扣血，但预览按效果自己的 key 找触发器，不要互相 spawn。

参考：`文档/子系统/UI/效果预览系统.md`

## D. action / reaction 断链

### D1. reaction 引用了未定义的 action 名

错例

```typescript
triggers: [{ when: "before", key: "attack", action: "reduceDamge" }],   // 拼错
reaction: {
    reduceDamage: [{ ... }]   // 真名
}
```

结果
    触发器识别不到 reduceDamge，reaction 静默失效

正解
    确保 triggers 的 action 字符串与 reaction 段的 key 完全一致

### D2. 只写 triggers 不写 reaction

除了 `cancelEvent: true` 这类"直接结论"的触发器，一般写 triggers 都要有对应 reaction

例外

```typescript
// 壁垒：直接阻止事件，不需要 reaction
triggers: [{ when: "before", how: "take", key: "clearArmor", cancelEvent: true }]
```

### D3. targetType 用错

reaction 段的 `targetType` 决定 effect 作用于谁：

    `owner` — 触发器所在实体的持有者（比如器官的持有玩家）
    `triggerOwner` — 触发事件的实体的持有者
    `triggerSource` — 触发事件的源头（谁打了我）
    `triggerEffect` — 修改触发事件本身的参数（改伤害值用这个）
    `allAllies` — 所有友军
    `allOpponents` — 所有敌方

对照

    改伤害值 → `triggerEffect`
    自己回血 → `owner`
    反击攻击者 → `triggerSource`
    给全体队友加 buff → `allAllies`

错例

```typescript
// 想改伤害值却用了 owner
reaction: {
    boost: [{
        targetType: "owner",   // 错，应该是 triggerEffect
        effect: [{ key: "modifyDamageValue", params: { delta: 3 } }]
    }]
}
```

## E. 数据结构位置

### E1. 卡牌 cost 写在顶层

错例

```typescript
{ label: "打击", cost: 1, status: { damage: 5 } }
```

正解

```typescript
{ label: "打击", status: { cost: 1, damage: 5 } }
```

原因
    cost 是可被修饰器修改的属性，必须在 status 内才能被 modifier 追踪

### E2. target 用 { key: "enemy" }

错例

```typescript
target: { key: "enemy" }
```

正解

```typescript
target: { faction: "opponent" }
target: { faction: "enemy" }
target: { key: "self" }
```

规律
    「self」用 `key`
    阵营（opponent / enemy / player / all）用 `faction`
    两者互斥

### E3. pool 写成字符串

错例

```typescript
pool: "common"
```

正解

```typescript
pool: ["common"]
```

pool 是数组，可以同时属于多个池（如 `["common", "shop"]`）

### E4. rarity 用不存在的值

有效值
    卡牌 / 器官 / 遗物 rarity 都是三档：`common` / `uncommon` / `rare`
    没有 `unique` / `legendary` / `epic`

器官 rarity 用枚举
    `OrganRarity.Common` / `OrganRarity.Uncommon` / `OrganRarity.Rare`

遗物 rarity 用字符串
    `"common"` / `"uncommon"` / `"rare"`

### E5. entry 写在错误位置或用错值

有效 card entry 值
    `card_exhaust` / `card_void` / `card_inherent` / `card_cannot_play` / `exhaust`

遗物没有 entry 字段
    RelicMap 不支持 entry，别写

状态没有 entry 字段
    StateData 不支持 entry

## F. 多段与群体

### F1. 多段攻击写成多个 attack effect

错例

```typescript
effects: [
    { key: "attack", params: { value: 4 } },
    { key: "attack", params: { value: 4 } },
    { key: "attack", params: { value: 4 } }
]
```

正解

```typescript
effects: [{
    key: "repeatEffects",
    params: {
        times: 3,
        effects: [{ key: "attack", params: { value: 4 } }]
    }
}]
```

原因
    并列多个 attack 事件独立结算，每次都走完整的伤害修饰器 / 护甲扣减 / 死亡检测流程 — 语义与"多段攻击"不等价
    repeatEffects 内的重复视为一次连续动作，是多段的正确语义

### F2. 群体效果的 EffectFunc 没处理数组 target

症状
    自定义效果对多个敌人时只有第一个生效

原因
    自定义 EffectFunc 里 `event.target` 可能是数组

正解
    用 `handleEventEntity` 包裹或手写循环

```typescript
export const myEffect: EffectFunc = (event, effect) => {
    handleEventEntity(event.target, target => {
        // 对每个 target 执行
    })
    return true
}
```

### F3. target: { number: 3 } vs number: "all"

    `{ number: 3 }` — 至多 3 个
    `{ number: "all" }` — 全体
    不写 number — 单个

## G. 状态定义细节

### G1. allowNegative 未开导致 buff 无法削弱

症状
    给力量施加 -2 时，力量停在 0 而不是变成 -2

正解

```typescript
{ label: "力量", allowNegative: true }
```

规律
    可能被削弱到负数的 buff 都要开 allowNegative
    debuff 通常不需要（虚弱扣到 0 就自动消失符合直觉）

### G2. showType: "bool" 但代码依赖层数

症状
    UI 只显示"有/无"，但代码里判断层数值，玩家看不到强弱

正解
    要么 showType 用 `"number"`
    要么确保 bool 状态真的只是标记，不承载数值

### G3. 忘写 stackChange 导致 debuff 永不消失

症状
    虚弱 / 易伤挂到玩家身上，回合结束不自动扣层

正解

```typescript
stackChange: [{ timing: "turnEnd", delta: -1 }]
```

规律
    经典 SL 类 debuff（虚弱 / 易伤 / 中毒）都应该有衰减规则
    没有衰减规则的持续 debuff 只到战斗结束才消失
    中毒是例外：它在回合开始结算伤害（必须排在护甲清零之后），衰减也跟着挂在
    `timing: "turnStart"` + `when: "after"` + 低 level，排在扣血之后。
    详见 `文档/开发指南/状态系统开发指南.md` 的 stackChange 小节

### G4. delta: "all" 与常量的语义混淆

    `delta: -1` — 减 1 层
    `delta: -5` — 减 5 层
    `delta: "all"` — 清零（不管当前多少层）

### G5. stateKey 拼错

错例

```typescript
{ key: "applyState", params: { stateKey: "vulnrable", stacks: 2 } }
```

排查
    stateKey 必须与 stateList.ts 中定义的 key 完全一致
    常见拼错：vulnerable / vulnrable / vunerable

## H. 表达式与引用

### H1. $triggerEffect.params(...) 拿不到值

症状
    累计触发遗物永远不涨

原因
    不同事件的参数名不同：
    `damage` 事件用 `value`
    `applyState` 事件用 `stacks`
    `heal` 事件用 `value`
    `drawCard` 事件用 `value`

排查
    查触发事件的源头 effectMap 定义，确认参数名
    或改用常量：`gain: 1`

### H2. condition selfHealth 写成数字

错例

```typescript
condition: { selfHealth: 30 }
```

正解

```typescript
condition: { selfHealth: { below: 30 } }
condition: { selfHealth: { above: 30 } }
condition: { selfHealth: { equals: 100 } }
```

规律
    condition 里所有数值条件都必须包在 `{ below/above/equals: N }` 结构里

### H3. $owner.hpPercent vs $owner.hp

    `$owner.hpPercent` — 0.0 到 1.0 的百分比
    `$owner.current.health` — 具体数值
    `$owner.status(max-health)` — 上限

用错很容易，看条件语义决定用哪个

### H4. $owner.status(key) 引用不存在的 key

症状
    数值恒为 undefined 或 0

排查
    确认 status 字段真的存在于该实体（比如 `damage` 是卡牌上的，不是玩家上的）
    表达式里的 key 名要与 status 字段的实际名字对齐（`max-health` 不是 `maxHealth`）

### H5. 找不到参与者 item

症状
    控制台 `找不到参与者: item`。第一行 Message 会带询问方（器官/卡/遗物的 label 和 key）

原因
    条件里 `$item` 是物品、`$owner` 是持有者。效果参数里两者都指向定义该 EffectUnit 的物品。

排查
    看报错「询问方」是谁
    效果参数用 `$item.status(...)` 或 `$owner.status(...)` 都可以
    条件里读持有者属性必须用 `$owner`，读物品自身用 `$item`

## I. 描述文本

### I1. describe 里引用了不存在的 status

错例

```typescript
status: { damage: 5 },
describe: ["造成", { key: ["status", "dmg"] }, "点伤害"]   // key 名错了
```

结果
    UI 显示 undefined 或空

正解
    key 数组要与 status 字段名完全一致

### I2. { "@": N } 索引越界

错例

```typescript
cards: ["card_a"],
describe: ["提供", { "@": 0 }, "和", { "@": 1 }, "卡"]   // cards 只有 1 张
```

规律
    `{ "@": N }` 索引对应 cards 数组下标
    N 必须 < cards.length

### I3. describe 里硬编码数值

不推荐

```typescript
status: { damage: 5 },
describe: ["造成 5 点伤害"]   // 硬编码 5
```

推荐

```typescript
describe: ["造成", { key: ["status", "damage"] }, "点伤害"]
```

原因
    升级 / 修饰器改 status 值时描述自动同步
    硬编码会导致「描述 5 点，实际 8 点」的错乱

## J. AI behavior

### J1. patterns 顺序反了

规则
    高 priority 优先评估
    priority 相同时按数组顺序
    「更特化」的条件放前面

错例

```typescript
patterns: [
    { priority: 0, condition: {}, action: ... },        // 无条件
    { priority: 10, condition: { selfHealth: { below: 30 } }, action: ... }   // 血低时用
]
```

问题
    优先级评估看起来 priority 10 优先，但 priority 相同或都不匹配时按顺序。实际语义容易出错

正解
    要么调换顺序，要么把 fallback 放到 behavior.fallback 而不是 patterns 里

### J2. sequence mode 忘写 sequence

错例

```typescript
action: { selector: {}, mode: "sequence" }   // 没 sequence 数组
```

结果
    退化成 random，行为不符预期

### J3. battleList 覆盖 behavior 是完全替换

症状
    在 battleList 里想只改一个 pattern，结果 fallback 消失

原因
    behavior 覆盖是**完全替代**，不是深度合并

正解
    要么复制原 behavior 完整重写
    要么把变体做成独立的 enemy key

### J4. organ 数组是必需字段

即使敌人不需要器官提供的效果，也不能省略 organ 字段。用空数组 `organ: []`

### J5. 多行动用了 actions-per-turn 而不是 moves

症状
    充能满了连放两发放电，或第二动仍抽到同一张条件牌

原因
    `actions-per-turn` 把同一套 pattern 独立评 n 次，两次看到的状态相同

正解
    一招要打出多张、或某回合只打一张 → `behavior.moves`（场景 4）
    真的要独立抽两次才写 `actions-per-turn`

## K. 设计原则违反

### K1. 器官对称原则违反

错例
    在 reaction 里判断 `$owner.isEnemy` 走不同分支
    Boss 时对玩家施 2 层毒，玩家用时对敌人只施 1 层

正解
    删掉分支，两边效果完全一致
    如果真的需要区分，拆成两个器官，不是一个器官双模式

参考：memory feedback_organ_symmetry

### K2. 器官独立原则违反

错例
    某器官必须搭配另一个器官才生效，孤立时毫无效果

正解
    加保底收益：即使联动不成立，也给个 +X 生命 / +Y 物质
    「联动强 / 独立弱但仍生效」可接受
    「独立完全无效」必须换极强的独立收益补偿

参考：memory feedback_organ_standalone

### K3. Boss 专属卡忘加 "enemy" tag

症状
    Boss 的强卡出现在玩家奖励池 / 商店

正解

```typescript
{
    label: "熔炉打击",
    key: "boss1_card_forge_strike",
    tags: ["attack", "enemy"]   // enemy tag 关键
}
```

规律
    Boss / 精英 / 敌人专属卡都应该有 "enemy" tag
    池抽卡时会自动过滤 "enemy" tag

### K4. 玩家 / 敌人器官 max-mass 差距太大

现象
    Boss 器官 max-mass 通常 30-50+，玩家自选器官 15-25
    这不是错，是设计意图（Boss 器官更耐损坏）

需要注意
    玩家吞噬 Boss 器官后，max-mass 值不变（保持大值）
    这是"捡到大件"的正反馈，不要在 possess 里自动降级

症状
    战利品还剩药水没领就点了前进，关地图后奖励界面没了

原因
    「前进」曾经会清空奖励列表再打开地图。药水栏满时领取失败，列表却已经被清掉。

## Vue 响应式陷阱

### 保护 Status 对象不被响应式破坏

Status 对象内部有 `ref()` 字段，存入 entity.status 时必须用 `markRaw()`：

```typescript
entity.status[key] = markRaw(status)   // 正确
entity.status[key] = status            // 错误，Vue 会破坏内部 ref
```

## L. 模块加载顺序

三种延迟手段不要混用：

```
懒加载 getLazyModule     数据表（organList、cardList、effectMap）
工厂 createOrgan 等      只负责 new + initialize()，不是加载隔离
动态 import()            只在 preload.ts、lazyLoader 的 loader、initContainer()
preload.ts               按继承链分层加载（先 Target，后 Player）
```

`import type` 不参与运行时求值。能改成 type 导入就不要改成动态 import。核心类里散 `await import("@/core/factories")` 是错的。

### L1 Cannot access 'Chara' before initialization

状态
    已修（2026-09-09）。工厂要不要长期保留另议，见 `文档/任务列表.md`。

症状
    启动报 `Uncaught ReferenceError: Cannot access 'Chara' before initialization`，堆在 `Player.ts` 的 `class Player extends Chara`

为什么
    ESM 值导入会立刻求值。preload 加载 `Target.ts` 时，`Chara` 还没写完。
    `factories.ts` 若顶层值导入 `Player` / `Enemy`（都 `extends Chara`），任何此时碰到工厂的链路都会提前执行子类：
    `Target` → `OrganModifier` → `CardModifier` → `cardList` → `factories` → `Player`
    旁路：`Organ` / `ItemModifier` → `battle` → `run` → `factories`。

不要
    在 `Target` / `Player` 里 `await import("@/core/factories")`
    把工厂加成第二套 preload 来当加载隔离
    `describe.ts` 值导入 `cardSegment.ts`（描述层拼卡名用 `getCardModifier` 和 `cardList`）

这次怎么修
    `createPlayer` / `createEnemy` 在函数内部再取类，顶层只 `import type`。调用处（`createOrgan`、`Target.ts`）不动。
    `Card.ts` 里 `Target` 只作类型，改成 `import type`。
    工厂仍然只是 `new` + `initialize()`。

### 别用 require()

本项目是 Vite + ES Modules
    错：`const cardList = require('@/static/list/item/cardList')`
    对：数据表用 `getLazyModule('cardList')`；只有 lazyLoader 自己的 loader 里才写 `await import('@/static/list/item/cardList')`

## 快速排查流程

写完新内容后按以下顺序自查：

    数据结构：cost / target / pool 位置对吗
    修饰器：写了不必要的 lose 段吗；current 数组齐吗
    触发器：when / how / key 匹配语义吗；battleStart 类要不要加 disableUntil
    action 链：triggers.action 与 reaction key 完全一致吗；targetType 对吗
    表达式：$xxx 语法对吗；condition 数值都包在 { below/above } 里吗
    描述：{ key: [...] } 引用的 status 存在吗；{ "@": N } 索引不越界吗
    多段：用 repeatEffects 不是并列 damage 吗
    状态：allowNegative 该开的开了吗；stackChange 该有的有吗
    Boss：卡有 "enemy" tag 吗；器官没写双模式吗
    模块：核心类有没有 await import 工厂；加载 Target 的链路有没有提前 import 会值导入 Player 的 factories
